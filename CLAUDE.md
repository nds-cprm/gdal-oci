# CLAUDE.md

Este arquivo orienta o Claude Code (claude.ai/code) ao trabalhar neste repositório.

## Visão geral

Imagem Docker base com **GDAL compilado a partir do código-fonte**, com suporte a **Oracle (OCI)**, **Apache Arrow/Parquet**, PostGIS, Elasticsearch, GeoPackage, OpenFileGDB, COG, KML/KMZ e serviços OGC (WMS/WFS/WCS/OGC API), mais os bindings Python do GDAL instalados em um virtualenv. Tudo é instalado sob `BASE_DIR=/opt/geosgb`.

O repositório contém o [README.md](README.md) (documentação para quem usa as imagens `devel`/`release` como base; manter em sincronia com o Dockerfile), o [Dockerfile](Dockerfile), o [docker-entrypoint.sh](docker-entrypoint.sh), os scripts de inicialização em [docker-entrypoint.d/](docker-entrypoint.d/), os exemplos de imagens derivadas em [examples/](examples/) (cada subdiretório com Dockerfile e README; a imagem base entra por `GDAL_IMAGE`/`GDAL_TAG`, então dá para testar com tags locais via `--build-arg`), as dependências do venv em [requirements/](requirements/) (`venv.in` → `venv.txt` com hashes, via pip-compile), o gerador de SBOM [sbom/cyclonedx.py](sbom/cyclonedx.py) (usado no build via bind mount, não fica na imagem), o VEX em [vex/](vex/), as pendências em [TODO.md](TODO.md), a [LICENSE](LICENSE) (Apache 2.0) e o CI em [.github/](.github/).

Esta imagem servirá de base para outras imagens de aplicação Python com GDAL

## CI ([docker-image.yml](.github/workflows/docker-image.yml))

Disparado manualmente (`workflow_dispatch`) e toda segunda às 03:00 UTC (`schedule`, só no branch padrão; o GitHub desativa schedules de repositórios públicos sem atividade por 60 dias). Push/PR comentados. Três jobs:

- **`build`** (por arquitetura, em runner nativo: `amd64` em `ubuntu-24.04`, `arm64` em `ubuntu-24.04-arm`): build do `devel` e depois do `release` no mesmo builder (as duas saem do mesmo build do GDAL), push só por digest, attestations de SBOM e provenance (`sbom: true`, `provenance: mode=max`; o `imagetools create` as preserva nas tags), cache GHA com `cache-to` apenas no `release` (o `mode=max` dele já cobre todos os estágios). O estágio `release` usa `no-cache-filters: release`: é sempre refeito (o `apt-get upgrade` e o `apt-get install` dos pacotes de runtime levam poucos minutos), então todo build recebe as correções atuais do Debian, inclusive nos pacotes que já vêm na `python:slim`, mesmo com o resto em cache. O `devel` também faz `apt-get upgrade` (primeiro `RUN`), mas essa camada fica em cache: só recebe atualizações do Debian quando a imagem base muda (`pull: true`) ou o cache é invalidado. Em seguida roda [smoke-test.sh](.github/scripts/smoke-test.sh) nas duas imagens.
- **`scan`** (por arquitetura, antes de existir qualquer tag): extrai a attestation de SBOM do digest do `release` (`imagetools inspect` + `jq`), roda o Docker Scout e o Grype e envia os SARIF para o code scanning (categorias `docker-scout-<arch>` e `grype-<arch>`). **Gate**: um segundo Grype com `only-fixed` + `severity-cutoff: critical` + o VEX de [vex/gdal-oci.openvex.json](vex/gdal-oci.openvex.json) falha o job. Ou seja, bloqueia vulnerabilidade **crítica com correção disponível** que não esteja no VEX. High e CVEs sem correção (a maioria dos do Debian, `no-dsa`) só vão para o code scanning. O Grype é necessário porque o Scout ignora os componentes de `${BASE_DIR}/share/sbom` (purls `generic`/`github`); o Grype os casa pelo CPE. Ele analisa a attestation e não a imagem, porque o Grype não lê CycloneDX embutido ao analisar uma imagem, e o Syft só lê com `--select-catalogers +sbom-cataloger` (ligado por padrão apenas no scanner do BuildKit). O passo falha se a attestation não tiver o `thrift`. Obs.: o SBOM do Syft também lê o `bom.cdx.json` que o pip traz em `pip/_vendor`, então as dependências vendorizadas do pip (urllib3, msgpack...) aparecem no relatório; só uma nova versão do pip as corrige.
- **`merge`** (`needs: [build, scan]`; falha no smoke test ou no gate = nenhuma tag): lê `GDAL_VERSION` e `PYTHON_VERSION` dos `ARG` do Dockerfile e cria as tags multi-arquitetura (ver política de tags).

Segurança do workflow: `permissions: contents: read` no topo (só o `scan` pede `security-events: write`), `actions/checkout` com `persist-credentials: false` e **todas as actions fixadas por SHA de commit** com a versão em comentário (`uses: owner/action@<sha> # vX.Y.Z`). O [Dependabot](.github/dependabot.yml) abre PR semanal atualizando SHAs e comentários (e outro para as dependências do venv). Ao adicionar uma action, fixá-la por SHA do mesmo jeito (resolver a tag com `api.github.com/repos/<owner>/<repo>/git/ref/tags/<tag>` e, se for tag anotada, desreferenciar em `git/tags/<sha>`). Requer os secrets `DOCKERHUB_USERNAME` e `DOCKERHUB_TOKEN` (usados no `build`, no `scan`, pois o Scout exige login, e no `merge`).

**VEX** ([vex/gdal-oci.openvex.json](vex/gdal-oci.openvex.json), OpenVEX): declara `not_affected` (`vulnerable_code_not_present`) para CVEs em código que a imagem não compila. Hoje: os do driver netCDF (CVE-2026-49014) e do HDF4/HDF-EOS (CVE-2026-8084/8086/8087/8088/8212/8213), com os GHSA correspondentes como statements próprios. Os produtos são purls **com versão** (`pkg:generic/osgeo/gdal@3.12.4` do SBOM embutido e `pkg:pypi/gdal@3.12.4` dos bindings): ao mudar `GDAL_VERSION`, as declarações deixam de valer e precisam ser revistas e atualizadas. Só incluir um CVE depois de confirmar que o código afetado não está na imagem (ex.: driver fora de `gdalinfo --formats`/`ogrinfo --formats`).

O smoke test também roda localmente: `sh .github/scripts/smoke-test.sh <imagem>`. Ele confere versões, a lista de drivers habilitados, escrita/leitura (COG, GPKG, KMZ, Parquet com cada codec), ausência de `libthrift` do Debian, os SBOMs de `${BASE_DIR}/share/sbom`, as proteções de compilação (só no `devel`, que tem `readelf`), bindings Python e o nss_wrapper com `--user 12345:0` (usuário virtual, `HOME`, diretório exclusivo 0700, `USER_NAME` personalizado e recusa de `USER_NAME` com `:`). **Ao habilitar ou remover um driver no Dockerfile, atualizar `RASTER_DRIVERS`/`VECTOR_DRIVERS` no script.**

## Build

O último estágio (`release`) é o alvo padrão; use `--target devel` para a imagem de desenvolvimento.

```bash
docker build --target devel -t docker.io/ndscprm/gdal:3.12.4-py3.12-devel .
docker build -t docker.io/ndscprm/gdal:3.12.4-py3.12 .
# arquitetura específica (x64 e arm64 são suportadas)
docker buildx build --platform linux/arm64 -t docker.io/ndscprm/gdal:3.12.4-py3.12 .
```

**Política de tags** (repositório `docker.io/ndscprm/gdal`): `<GDAL_VERSION>-py<PYTHON_VERSION>` para o `release` e o mesmo com sufixo `-devel` para o `devel` (ex.: `3.12.4-py3.12` / `3.12.4-py3.12-devel`). Essas tags são móveis: cada build (manual ou semanal) as atualiza. Cada build cria também tags datadas imutáveis, `<GDAL_VERSION>-py<PYTHON_VERSION>-<YYYYMMDD>` e `...-<YYYYMMDD>-devel` (UTC). Se já existir uma tag do mesmo dia, usa `<YYYYMMDD>.2`, `.3`... e nunca sobrescreve. As tags de um mesmo build saem sempre juntas: build do `devel` primeiro, depois do `release`, que reaproveita o cache. Debian, Arrow, Oracle e numpy não entram na tag. Ao mudar `GDAL_VERSION` ou `PYTHON_VERSION`, o nome das tags muda junto; os comandos de build/push estão no [README.md](README.md#build).

Verificação rápida após o build:

```bash
docker run --rm docker.io/ndscprm/gdal:3.12.4-py3.12 gdalinfo --version
docker run --rm docker.io/ndscprm/gdal:3.12.4-py3.12 ogrinfo --formats | grep -Ei 'oci|parquet|arrow'
docker run --rm docker.io/ndscprm/gdal:3.12.4-py3.12 /opt/geosgb/venv/bin/python -c "from osgeo import gdal; print(gdal.__version__)"
```

## Estrutura do Dockerfile

Três estágios:

- **`devel`** (`python:${PYTHON_VERSION}-${DEBIAN_VERSION}`): toolchain, headers, código-fonte do GDAL, símbolos de debug e `gdb`. Usado para depurar e compilar código dependente do GDAL.
- **`staging`** (`FROM devel`, descartável): remove de `${BASE_DIR}` os arquivos só de build (`src`, `include`, `lib/cmake`, `lib/pkgconfig`, `*.a`, SDK do Oracle), faz `strip --strip-debug` em `bin`, `lib` e nos módulos `osgeo` do venv, e gera `/tmp/runtime-packages.txt` com os pacotes Debian de runtime: roda `ldd` nos binários do GDAL (transitivo, inclui o Oracle client), resolve com `realpath` e mapeia com `dpkg -S`. O build falha se algum `ldd` der `not found` ou se uma lib não pertencer a nenhum pacote.
- **`release`** (`python:${PYTHON_VERSION}-slim-${DEBIAN_VERSION}`): copia os `ld.so.conf.d` do staging, instala a lista de pacotes (bind mount, sem ficar na imagem), copia `${BASE_DIR}`, recria o symlink `libaio.so.1`, repete os `ENV` e define `ENTRYPOINT ["/docker-entrypoint.sh"]` + `CMD ["python3"]`. O venv funciona porque o python das imagens `python` e `python:*-slim` fica no mesmo caminho (`/usr/local/bin`).

Etapas do `devel`, em ordem:

1. **Ferramentas de build** — `apt-get upgrade` (correções do Debian publicadas depois da imagem base) e `build-essential`, `cmake`, `gdb`, `wget`, `unzip`, etc. Para usar o `gdb` no container: `docker run --cap-add=SYS_PTRACE --security-opt seccomp=unconfined ...`.
2. **Oracle Instant Client 19.32** (basiclite + SDK) — baixado de `download.oracle.com` (a URL é derivada de `ORACLE_INSTANTCLIENT_VERSION`), validado por SHA256 por arquitetura (`ORACLE_*_SHA256_X64` / `_ARM64`), extraído em `${BASE_DIR}/oracle`. Cria o symlink `libaio.so.1` (Debian trixie só fornece `libaio.so.1t64`) e registra o diretório do client em `/etc/ld.so.conf.d/oracle.conf`.
3. **Dependências do GDAL** — pacotes `-dev` do Debian, incluindo os usados no build do Arrow (Boost headers, codecs brotli/bz2/lz4/snappy/zlib/zstd, re2, utf8proc).
4. **Apache Thrift + Apache Arrow/Parquet do código-fonte** — não usam o repositório apt do Arrow, porque os pacotes dele linkam o `libthrift` do Debian (0.19 no trixie, com CVEs abertos marcados `no-dsa`). Os tarballs vêm de `dlcdn.apache.org` (com fallback para `archive.apache.org`, para onde vão as versões antigas) e são validados por `THRIFT_SHA256`/`ARROW_SHA256`.
   - **Thrift**: só a biblioteca C++, estática e PIC (`BUILD_SHARED_LIBS=OFF`), sem compilador, TLS, zlib ou libevent. Ela fica embutida no `libparquet.so`, então não aparece no `dpkg`. Os scanners a enxergam pelo SBOM embutido (`apache-arrow.cdx.json`, com CPE), e o Grype do CI a verifica a cada build.
   - Os dois são compilados com `HARDENING_CFLAGS`/`HARDENING_LDFLAGS` (o Thrift é estático, então só as `CFLAGS` se aplicam).
   - **Arrow**: `ARROW_DEPENDENCY_SOURCE=SYSTEM`, só bibliotecas compartilhadas (`ARROW_BUILD_STATIC=OFF`), módulos `COMPUTE`, `ACERO`, `DATASET`, `FILESYSTEM`, `IPC` e `PARQUET`, todos os codecs, sem jemalloc/mimalloc. `xsimd` e `simdjson` são `BUNDLED` porque o Arrow exige versões mais novas que as do trixie; o Arrow os baixa do GitHub e valida pelo SHA256 do seu `cpp/thirdparty/versions.txt` (que vem no tarball verificado).
   - Tudo é instalado em `${BASE_DIR}` (`lib`, `include`, `lib/cmake`), e `${BASE_DIR}/lib` é registrado em `/etc/ld.so.conf.d/geosgb.conf`, pois os binários instalados não têm RPATH. O `staging` remove `libthrift.a`, headers e CMake junto com os do GDAL.
5. **Virtualenv Python** em `${BASE_DIR}/venv`: `pip install --require-hashes -r requirements/venv.txt` (bind mount) instala versões fixas de pip, setuptools e wheel (build dos bindings) e numpy (necessário antes do GDAL para os bindings com suporte a arrays).
6. **GDAL** — baixado de `download.osgeo.org`, validado pelo SHA256 fixo em `GDAL_SHA256`, compilado com CMake (`RelWithDebInfo` fixo, com `-O3 -g -DNDEBUG` para manter a otimização do `Release`, mais `HARDENING_CFLAGS`/`HARDENING_LDFLAGS`. Os módulos Python (`_gdal*.so`) são compilados pelo setuptools (`setup.py build_ext`), que lê `CFLAGS`/`CXXFLAGS`/`LDFLAGS` do ambiente e, quando elas existem, **descarta** as flags do Python (`-O3 ...`). Por isso o `cmake --build` recebe `CFLAGS`/`CXXFLAGS` = flags do `sysconfig` + `HARDENING_CFLAGS`. Sem isso os wrappers saem sem otimização, o que o smoke test acusa como falta de `_FORTIFY_SOURCE`; símbolos ficam no `devel` e são removidos no `staging`; prefixo `${BASE_DIR}`, bindings Python compilados com o python do venv e instalados nele via `GDAL_PYTHON_INSTALL_PREFIX`; `CMAKE_PREFIX_PATH=${BASE_DIR}` para encontrar o Arrow da etapa 4; build paralelo com `--parallel "$(nproc)"`).
7. `ENV GDAL_DATA=${BASE_DIR}/share/gdal`, `VIRTUAL_ENV=${BASE_DIR}/venv` e `PATH` com `${BASE_DIR}/venv/bin` antes de `${BASE_DIR}/bin` (o `python`/`pip` do shell resolvem para o venv, sem precisar de `activate`).

## Convenções

- `SHELL` usa `bash -o pipefail` no `devel` (volta para `/bin/sh -c` no final) e no `staging`; o `release` usa o shell padrão.
- Cada `RUN` com apt faz `update`, `install --no-install-recommends --no-install-suggests`, `autoremove` e apaga `/var/lib/apt/lists/*`. O primeiro `RUN` do `devel` e o `RUN` de pacotes do `release` fazem também `DEBIAN_FRONTEND=noninteractive apt-get -y upgrade` logo após o `update`, para aplicar nos pacotes da imagem base as correções do Debian publicadas depois dela.
- Todo download externo é verificado contra um valor fixado no repositório (SHA256 do Oracle, do Thrift, do Arrow e do GDAL no Dockerfile; hashes dos pacotes do venv em `requirements/venv.txt`), nunca contra um checksum baixado do mesmo servidor. Ao atualizar uma versão, atualize também o checksum/fingerprint correspondente.
- A arquitetura do Oracle é derivada de `dpkg --print-architecture` (`amd64` → `x64`); arquiteturas diferentes de x64/arm64 abortam o build.

## Pontos de atenção (estado atual)

- **Drivers opcionais**: `GDAL_BUILD_OPTIONAL_DRIVERS=OFF` e `OGR_BUILD_OPTIONAL_DRIVERS=OFF` desativam todos os drivers opcionais; OCI, Arrow, Parquet, OpenFileGDB, PostGIS (`PG` + `PGDump`, e `POSTGISRASTER`) e GeoPackage (`GPKG` + `SQLite`, com `PNG`/`JPEG` para tiles raster) e serviços OGC (`WMS`, `WCS`, `OGCAPI`, `WFS`, `OAPIF`, mais `RAW` exigido no configure pelo WMS, e `GML` e `MVT` usados em runtime por WFS e OGC API Tiles) KML/KMZ (`KML` e `LIBKML`) e `Elasticsearch` (`ELASTIC`, via cURL) são habilitados explicitamente (`OGR_ENABLE_DRIVER_*`/`GDAL_ENABLE_DRIVER_*=ON`), com `GDAL_USE_ORACLE/ARROW/PARQUET/POSTGRESQL/SQLITE3/CURL/EXPAT/LIBKML=ON` para o configure falhar se a dependência não for encontrada. Qualquer outro driver opcional precisa ser adicionado da mesma forma.
- O código-fonte do GDAL é mantido de propósito em `${BASE_DIR}/src/gdal-${GDAL_VERSION}` (depuração e compilação de código dependente do GDAL); só o diretório `build/` é removido após o install. O `cd` para o build fica num subshell `( ... )`, então comandos após o `)` rodam em `/tmp`.
- **SBOM**: os pacotes Debian e Python entram no SBOM do BuildKit automaticamente, mas o que é compilado ou baixado fora do apt não. Por isso cada etapa que instala algo assim grava um CycloneDX em `${BASE_DIR}/share/sbom/*.cdx.json` com [sbom/cyclonedx.py](sbom/cyclonedx.py) (`RUN --mount=type=bind,source=sbom/cyclonedx.py,...`): `oracle-instantclient`, `apache-arrow` (arrow, thrift, xsimd, simdjson; as versões de xsimd/simdjson vêm do `versions.txt` do Arrow) e `gdal`. O Syft do BuildKit incorpora esses componentes na attestation. Componente com CVE conhecido precisa de `cpe` (vendor/produto da NVD); o Oracle fica sem CPE de propósito, porque os CPEs da Oracle na NVD são do servidor de banco e dariam falsos positivos. **Novo componente fora do apt = nova entrada no SBOM** (o smoke test confere os nomes esperados).
- Os pacotes de runtime do `release` não são listados à mão: vêm do `ldd` no `staging`. Ao adicionar um driver/dependência, não é preciso mexer no `release`. Pacotes que o GDAL só carrega em runtime sem linkar (ex.: dados) precisam ser adicionados explicitamente.
- **Entrypoint (`devel` e `release`)**: definido no `devel` (que o `staging` herda); o `release` copia `/docker-entrypoint.sh` e `/docker-entrypoint.d` do `staging` com `COPY --from`, que preserva os modos, para as duas imagens terem sempre o mesmo entrypoint. [docker-entrypoint.sh](docker-entrypoint.sh) (POSIX `sh`) percorre `/docker-entrypoint.d` em ordem léxica — mesmo modelo da imagem oficial do Postgres: `*.sh` com `+x` são executados, `*.sh` sem `+x` são carregados com `.` (variáveis exportadas chegam ao comando; `exit` neles, mesmo `exit 0`, interrompe o start), o resto é ignorado. Termina com `exec "$@"`. A permissão define o modo, então imagens derivadas devem usar `COPY --chmod`. Script com erro aborta o start (`set -e`). `ENTRYPOINT_QUIET_LOGS` silencia os logs. O `CMD ["python3"]` é explícito porque definir `ENTRYPOINT` zera o `CMD` herdado da imagem `python`; imagens derivadas que definirem só `CMD` continuam passando pelo entrypoint.
- **nss_wrapper (`devel` e `release`)**: o pacote `libnss-wrapper` é instalado explicitamente nos dois estágios (no `release`, à parte da lista do `ldd`, porque é carregado via `LD_PRELOAD` e não linkado) e [10-enable-nss-wrapper.sh](docker-entrypoint.d/10-enable-nss-wrapper.sh) (sem `+x`, portanto carregado com `.`) cria, quando o UID do container não existe no `/etc/passwd` (ex.: OpenShift, `--user`), um usuário virtual `${USER_NAME:-sgb}` e exporta `NSS_WRAPPER_PASSWD`, `NSS_WRAPPER_GROUP` e `LD_PRELOAD=libnss_wrapper.so`. Os arquivos `passwd`/`group` virtuais ficam num diretório criado com `mktemp -d` (`${TMPDIR:-/tmp}/nss_wrapper.XXXXXX`, modo 0700), nunca num caminho fixo do `/tmp`, que poderia ter sido plantado antes (ex.: symlink num `/tmp` compartilhado entre containers). `USER_NAME` (letra ou `_` no início, depois `[A-Za-z0-9._-]`, até 32 caracteres) e `HOME` (sem `:` nem quebra de linha) são validados antes de entrar na linha do passwd; valor inválido aborta o start com mensagem no stderr. Nesse caso também exporta `HOME=/tmp` se o `HOME` for `/` (o Docker usa `/` para UID sem passwd) ou não gravável. A mensagem vai para o stderr e respeita `ENTRYPOINT_QUIET_LOGS` — scripts em `docker-entrypoint.d` nunca devem escrever no stdout, que é a saída do comando (ex.: `/vsistdout/`). Os scripts de `docker-entrypoint.d/` são copiados um a um com `COPY --chmod` explícito (o modo define executar vs. carregar, e não pode depender da permissão no disco); o diretório é criado antes com `RUN mkdir -p`, porque `COPY --chmod=644` também aplicaria `644` ao diretório e ele deixaria de ser acessível para usuários não root. Novo script no repositório = nova linha `COPY` no bloco do entrypoint do `devel` (o `release` recebe o diretório inteiro).
- **pip do sistema removido (`devel` e `release`)**: a imagem `python` traz um pip próprio em `/usr/local` (desatualizado, com CVEs) que ninguém usa, porque `pip` resolve para o venv. Ele é desinstalado com `/usr/local/bin/python3 -m pip uninstall`. O wheel do `ensurepip` fica, então `python3 -m venv` continua criando venvs com pip nas imagens derivadas (o smoke test confere as duas coisas).
- **Abertura de arquivos não confiáveis**: o README tem uma seção ("Abrindo arquivos enviados por usuários") com riscos e mitigações testados nesta imagem: SSRF via `.vrt` com `/vsicurl/` e via XML do driver WMS, `allowed_drivers`, `GDAL_SKIP`. Ao habilitar drivers de rede ou que abrem outros datasets, revisar essa seção.
- **Dependências do venv fixadas com hash** ([requirements/venv.in](requirements/venv.in) → [venv.txt](requirements/venv.txt)): para mudar uma versão (inclusive o numpy, que antes era o build arg `NUMPY_VERSION`), editar o `venv.in` e regenerar o `venv.txt` com o comando do cabeçalho do `venv.in`. O pip-compile grava os hashes de todos os arquivos da versão no PyPI, cobrindo amd64/arm64 e outras versões do Python. O Dependabot (ecossistema `pip`, diretório `/requirements`) abre PR semanal com atualizações. Manter numpy 2: bindings compilados com numpy 2 rodam com 1.x e 2.x; compilados com 1.x quebram (`ImportError`) quando a imagem derivada instala numpy 2. O smoke test confere se as versões instaladas são as do `venv.txt`.
- **Imagens base por tag, sem digest (decisão)**: `FROM python:${PYTHON_VERSION}-${DEBIAN_VERSION}` (e `-slim-`) sem `@sha256`, para o rebuild semanal pegar a base atualizada automaticamente. Fixar o digest exigiria o Dependabot, que não entende `FROM` com `ARG`, ou atualização manual, e a base só atualizaria quando alguém aprovasse a mudança. A reprodutibilidade vem do provenance (`mode=max` registra o digest exato de cada base em `materials`) e das tags datadas.
- `ENV` é repetido no `release` (não é herdado entre estágios com `FROM` diferentes); manter os dois em sincronia.

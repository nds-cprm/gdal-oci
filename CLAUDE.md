# CLAUDE.md

Este arquivo orienta o Claude Code (claude.ai/code) ao trabalhar neste repositório.

## Visão geral

Imagem Docker base com **GDAL compilado a partir do código-fonte**, com suporte a **Oracle (OCI)**, **Apache Arrow/Parquet**, PostGIS, Elasticsearch, GeoPackage, OpenFileGDB, COG, KML/KMZ e serviços OGC (WMS/WFS/WCS/OGC API), mais os bindings Python do GDAL e o **pyarrow** (compilado contra as mesmas bibliotecas do Arrow C++ que o GDAL usa) instalados em um virtualenv. Tudo é instalado sob `BASE_DIR=/opt/geosgb`.

O repositório contém o [README.md](README.md) (documentação para quem usa as imagens `devel`/`release-py`/`release-nopy` como base; manter em sincronia com o Dockerfile), o [Dockerfile](Dockerfile), o [docker-entrypoint.sh](docker-entrypoint.sh), os scripts de inicialização em [docker-entrypoint.d/](docker-entrypoint.d/), os exemplos de imagens derivadas em [examples/](examples/) (cada subdiretório com Dockerfile e README; a imagem base entra por `GDAL_IMAGE`/`GDAL_TAG`, então dá para testar com tags locais via `--build-arg`), as dependências do venv em [requirements/](requirements/) (`gdal-build.in` → `gdal-build.txt` e, só para o build do pyarrow, `pyarrow-build.in` → `pyarrow-build.txt`, com hashes, via pip-compile), o gerador de SBOM [sbom/cyclonedx.py](sbom/cyclonedx.py) (usado no build via bind mount, não fica na imagem), o VEX em [vex/](vex/), as pendências em [TODO.md](TODO.md), a [LICENSE](LICENSE) (Apache 2.0) e o CI em [.github/](.github/).

Esta imagem servirá de base para outras imagens de aplicação Python com GDAL. A variante `release-nopy` tem o mesmo runtime do GDAL sem Python, para aplicações que só usam os utilitários ou a API C/C++.

## CI

Dois workflows:

- [publish-image.yml](.github/workflows/publish-image.yml) (`Publish image`): publica a `ndscprm/gdal` e dispara as imagens derivadas. Só tem os gatilhos e os jobs `meta`, `image` e `dispatch`; o build, o teste, o scan e as tags ficam no reutilizável.
- [reusable-publish-image.yml](.github/workflows/reusable-publish-image.yml) (`Reusable: publish image`): workflow `workflow_call` com o build, o teste, o scan e as tags. Chamado pelo `publish-image.yml` deste repositório (`uses: ./.github/workflows/reusable-publish-image.yml`, a versão do mesmo commit) e pelo `publish-image.yml` das derivadas (mapserver-oci, mapproxy-oci e pygeoapi-oci, por `@main`). Assim, cada build da base também testa o reutilizável que as derivadas usam.

Os nomes seguem a função: `publish-image.yml` é o ponto de entrada nos quatro repositórios (o `dispatch` chama esse nome nas derivadas), e o prefixo `reusable-` marca o que só roda chamado por outro workflow (o GitHub não aceita subdiretórios em `.github/workflows/`). Os runs anteriores à troca de nomes ficam na aba *Actions* sob os nomes antigos (`Docker Image CI`, `OCI image`).

### Workflow reutilizável ([reusable-publish-image.yml](.github/workflows/reusable-publish-image.yml))

Entradas, campos das variantes e exemplo estão no [README.md](README.md#workflow-reutilizável); mantenha-os em sincronia com o arquivo. Jobs:

- **`prepare`**: resolve a versão (entrada `version` ou `ARG <version-arg>` do Dockerfile, conferida com `version-pattern`) e valida as **variantes** (entrada `variants`, JSON: nome `[a-z0-9_-]`, `tag` obrigatória, nomes e tags únicos, tag final válida), preenchendo os padrões; os outros jobs leem o JSON normalizado. O `cache-to` vai para a variante marcada ou, sem marcação, para a última.
- **`build`** (por arquitetura, em runner nativo: `amd64` em `ubuntu-24.04`, `arm64` em `ubuntu-24.04-arm`): gera com `jq` uma definição JSON do Bake (um alvo por variante) em `$RUNNER_TEMP` e roda o `docker/bake-action` com `source: .` (contexto local, não o Git context padrão desde a v6). Uma chamada só, num builder só: os estágios comuns às variantes são construídos uma vez. `pull: true`, push só por digest, attestations de SBOM e provenance (`mode=max`; o `imagetools create` as preserva nas tags), cache GHA no escopo `<nome da imagem>-<arch>` (`slug` do `prepare`, o mesmo usado nos artifacts de digests), registro de build guardado por 14 dias (`DOCKER_BUILD_RECORD_RETENTION_DAYS`). O digest de cada variante vem do `metadata` do Bake (`<alvo>.containerimage.digest`). Depois roda o campo `test` de cada variante com `bash -euo pipefail -c`, no checkout do chamador (o `actions/checkout` de um workflow reutilizável faz checkout do repositório que chamou), com `IMAGE_REF`, `VARIANT` e `ARCH`. Com `push: true`, a imagem foi enviada só por digest e não fica no armazenamento local, então o workflow faz `docker pull` dela antes do teste. Sem isso, um `docker image inspect` antes de qualquer `docker run` falha com `No such image` (aconteceu no mapproxy e no pygeoapi).
- **`scan`** (por arquitetura e variante com `scan: true`, antes de existir qualquer tag; com a lista vazia, o job é pulado e o `merge` aceita `skipped`): extrai a attestation de SBOM do digest (`imagetools inspect` + `jq`), confere nela os pacotes de `sbom-require` (`.packages[].name` do SPDX), roda o Docker Scout e o Grype e envia os SARIF para o code scanning (categorias `docker-scout-<variante>-<arch>` e `grype-<variante>-<arch>`). Com `fail-on-severity`, um segundo Grype com `only-fixed` + `severity-cutoff` + o VEX (`vex`) falha o job; sem ele, o scan só reporta (a política das derivadas).
- **`merge`** (`needs: [prepare, build, scan]`; falha num teste ou no scan de qualquer variante ou arquitetura = nenhuma tag): cria as tags multi-arquitetura, a móvel (`tag` da variante, com `{version}`) e a datada `<tag>-<AAAAMMDD>` (UTC; `.2`, `.3`... para builds seguintes no mesmo dia, calculado sobre a primeira variante e igual para todas). Saídas: `tags` (JSON com as tags criadas) e `images` (JSON, variante → tag datada fixada pelo digest do índice, `<imagem>:<tag>-<AAAAMMDD>@sha256:...`, lido com `imagetools inspect --format '{{.Manifest.Digest}}'`).
- **`push: false`**: saída `type=docker` (`<image>:ci-<variante>-<arch>`), sem attestations (o exportador `docker` não as aceita), sem login, sem `scan` e sem `merge`.

Ao mudar o workflow: rode o `actionlint`, teste os blocos `run` localmente quando mexer em `jq`/shell (extraia-os do YAML e rode com as variáveis de ambiente do passo) e lembre que a mudança vale na hora para todos os chamadores em `@main`, e no próximo build da base.

### Publicação da base ([publish-image.yml](.github/workflows/publish-image.yml))

Disparado manualmente (`workflow_dispatch`, com a entrada `dispatch-derived`) e toda segunda às 03:00 UTC (`schedule`, só no branch padrão; o GitHub desativa schedules de repositórios públicos sem atividade por 60 dias). Push/PR comentados. Três jobs:

- **`meta`**: lê o `ARG PYTHON_VERSION` do Dockerfile e monta as variantes, com os nomes dos estágios do Dockerfile: `release-py` (tag `{version}-py<PYTHON_VERSION>`), `devel` (`{version}-py<PYTHON_VERSION>-devel`) e `release-nopy` (`{version}-nopy`). O `{version}` é o `ARG GDAL_VERSION` (entrada `version-arg` do reutilizável). O `release-py` vem primeiro, porque o sufixo datado é calculado sobre a primeira variante, e grava o cache (`cache-to`): o build dele passa pelo `devel` e pelo `staging`, então o `mode=max` cobre todos os estágios. O `release-py` e o `release-nopy` usam `no-cache-filters` com o próprio estágio: são sempre refeitos (o `apt-get upgrade` e o `apt-get install` dos pacotes de runtime levam poucos minutos), então todo build recebe as correções atuais do Debian, inclusive nos pacotes que já vêm na `python:slim`, mesmo com o resto em cache. O `devel` também faz `apt-get upgrade` (primeiro `RUN`), mas essa camada fica em cache: só recebe atualizações do Debian quando a imagem base muda (`pull: true`) ou o cache é invalidado. O teste de cada variante é o [smoke-test.sh](.github/scripts/smoke-test.sh) (o `release-nopy` com o argumento `release-nopy`). Só o `release-py` e o `release-nopy` são escaneados.
- **`image`**: chama o reutilizável com `vex: vex/gdal-oci.openvex.json`, `fail-on-severity: critical` e `sbom-require: thrift`. **Gate**: bloqueia vulnerabilidade **crítica com correção disponível** que não esteja no [VEX](vex/gdal-oci.openvex.json), nas duas variantes escaneadas. High e CVEs sem correção (a maioria dos do Debian, `no-dsa`) só vão para o code scanning. O Grype é necessário porque o Scout ignora os componentes de `${BASE_DIR}/share/sbom` (purls `generic`/`github`); o Grype os casa pelo CPE. Ele analisa a attestation e não a imagem, porque o Grype não lê CycloneDX embutido ao analisar uma imagem, e o Syft só lê com `--select-catalogers +sbom-cataloger` (ligado por padrão apenas no scanner do BuildKit). O `sbom-require: thrift` faz o scan falhar se a attestation não tiver esses componentes. Obs.: o SBOM do Syft também lê o `bom.cdx.json` que o pip traz em `pip/_vendor`, então as dependências vendorizadas do pip (urllib3, msgpack...) aparecem no relatório; só uma nova versão do pip as corrige. As imagens recebem os labels `org.opencontainers.image.created`, `revision` e `source`, que o reutilizável sempre define.
- **`dispatch`** (`needs: image`, só com tags publicadas; no `schedule` sempre, no disparo manual se `dispatch-derived` estiver marcada): matriz com os repositórios das imagens derivadas (`mapserver-oci`, `mapproxy-oci`, `pygeoapi-oci`, do mesmo dono), que roda `gh workflow run publish-image.yml --repo <dono>/<repo> --ref main`. Assim o rebuild semanal da base reconstrói as derivadas sobre as tags novas. O `GITHUB_TOKEN` não dispara workflows de outro repositório, então cada job gera, com o `actions/create-github-app-token`, um token de curta duração do **GitHub App da organização**, restrito ao repositório do job (`repositories`) e a `permission-actions: write`, revogado no fim do job. O App precisa da permissão de repositório **Actions: Read and write** e estar instalado nos repositórios derivados. O disparo passa as imagens da saída `images` do reutilizável (`devel`, `release-py` e `release-nopy`: tag datada e digest) nas entradas `image_devel`/`image_py`/`image_nopy` (`gh workflow run ... -f`), que o workflow da derivada repassa em `build-args` como `GDAL_IMAGE_DEVEL`/`GDAL_IMAGE_PY`/`GDAL_IMAGE_NOPY`: as derivadas são construídas sobre as imagens exatas que este CI acabou de publicar, e o padrão do Dockerfile delas (as tags móveis) só vale sem essas entradas (build local, disparo manual). O esquema de nomes das tags fica só aqui. Todas as derivadas declaram as três entradas, mesmo as que não usam alguma (o mapproxy-oci e o pygeoapi-oci ignoram o `image_nopy`), para que o disparo seja o mesmo para todas; sem uma delas, o `gh workflow run` falha (`HTTP 422`). Configuração: a variável `DERIVED_IMAGES_APP_CLIENT_ID` (Client ID do App; variável, não secret, porque não é sigilosa e só variáveis podem ser lidas no `if`) e o secret `DERIVED_IMAGES_APP_PRIVATE_KEY` (chave privada `.pem`), no repositório ou na organização. Sem a variável, o job só emite um aviso e não falha; com a variável e sem a chave (ou com o App sem acesso), o job falha, depois das tags já publicadas. O cadastro do App, o teste, a manutenção e os erros comuns estão no [README.md](README.md#rebuild-das-imagens-derivadas); manter os dois em sincronia com o job. `permissions: {}`, porque não usa o `GITHUB_TOKEN`. O workflow chamado precisa ter `workflow_dispatch` e se chamar `publish-image.yml`; nova imagem derivada = novo item na matriz.

Segurança dos workflows: `permissions: contents: read` no topo (só o `scan` do reutilizável pede `security-events: write`, concedido pelo job `image` que o chama), `actions/checkout` com `persist-credentials: false` e **todas as actions fixadas por SHA de commit** com a versão em comentário (`uses: owner/action@<sha> # vX.Y.Z`). O [Dependabot](.github/dependabot.yml) abre PR semanal atualizando SHAs e comentários (e outro para as dependências do venv). Ao adicionar uma action, fixá-la por SHA do mesmo jeito (resolver a tag com `api.github.com/repos/<owner>/<repo>/git/ref/tags/<tag>` e, se for tag anotada, desreferenciar em `git/tags/<sha>`). Requer os secrets `DOCKERHUB_USERNAME` e `DOCKERHUB_TOKEN` (usados no `build`, no `scan`, pois o Scout exige login, e no `merge`) e, para o `dispatch`, a variável `DERIVED_IMAGES_APP_CLIENT_ID` e o secret `DERIVED_IMAGES_APP_PRIVATE_KEY` (opcionais).

**VEX** ([vex/gdal-oci.openvex.json](vex/gdal-oci.openvex.json), OpenVEX): declara `not_affected` (`vulnerable_code_not_present`) para CVEs em código que a imagem não compila. Hoje: os do driver netCDF (CVE-2026-49014) e do HDF4/HDF-EOS (CVE-2026-8084/8086/8087/8088/8212/8213), com os GHSA correspondentes como statements próprios. Os produtos são purls **com versão** (`pkg:generic/osgeo/gdal@3.12.4` do SBOM embutido, que também cobre o `release-nopy`, e `pkg:pypi/gdal@3.12.4` dos bindings): ao mudar `GDAL_VERSION`, as declarações deixam de valer e precisam ser revistas e atualizadas. Só incluir um CVE depois de confirmar que o código afetado não está na imagem (ex.: driver fora de `gdalinfo --formats`/`ogrinfo --formats`).

O smoke test também roda localmente: `sh .github/scripts/smoke-test.sh <imagem>`, e com Podman `DOCKER=podman sh .github/scripts/smoke-test.sh <imagem>` (o script passa `--passwd=false` aos `run` do Podman, que senão acrescenta o UID ao `/etc/passwd` e o nss_wrapper não entra em ação) (para o `release-nopy`: `sh .github/scripts/smoke-test.sh <imagem> release-nopy`, que troca as verificações do venv/pip por verificações de que não há Python; a do SBOM é em `sh` e vale para todas). Ele confere versões, a lista de drivers habilitados, escrita/leitura (COG, GPKG, KMZ, Parquet com cada codec), ausência de `libthrift` do Debian, os SBOMs de `${BASE_DIR}/share/sbom`, as proteções de compilação (só no `devel`, que tem `readelf`; inclui os módulos do pyarrow), bindings Python, o pyarrow (versão igual a `ARROW_VERSION`, nenhum `libarrow*.so` próprio, as libs carregadas vêm de `${BASE_DIR}/lib`, ida e volta GDAL ↔ pyarrow via ArrowStream e Parquet) e o nss_wrapper com `--user 12345:0` (usuário virtual, `HOME`, diretório exclusivo 0700, `USER_NAME` personalizado e recusa de `USER_NAME` com `:`). **Ao habilitar ou remover um driver no Dockerfile, atualizar `RASTER_DRIVERS`/`VECTOR_DRIVERS` no script.**

## Build

O último estágio (`release-py`) é o alvo padrão; use `--target devel` para a imagem de desenvolvimento e `--target release-nopy` para a sem Python.

```bash
docker build --target devel -t docker.io/ndscprm/gdal:3.12.4-py3.12-devel .
docker build -t docker.io/ndscprm/gdal:3.12.4-py3.12 .
docker build --target release-nopy -t docker.io/ndscprm/gdal:3.12.4-nopy .
# arquitetura específica (x64 e arm64 são suportadas)
docker buildx build --platform linux/arm64 -t docker.io/ndscprm/gdal:3.12.4-py3.12 .
```

**Política de tags** (repositório `docker.io/ndscprm/gdal`): `<GDAL_VERSION>-py<PYTHON_VERSION>` para o `release-py` e o mesmo com sufixo `-devel` para o `devel` (ex.: `3.12.4-py3.12` / `3.12.4-py3.12-devel`). Essas tags são móveis: cada build (manual ou semanal) as atualiza. O `release-nopy` não tem Python, então a tag dele é `<GDAL_VERSION>-nopy` (ex.: `3.12.4-nopy`). Cada build cria também tags datadas imutáveis, sempre a tag móvel com `-<YYYYMMDD>` (UTC) no fim: `3.12.4-py3.12-<YYYYMMDD>`, `3.12.4-py3.12-devel-<YYYYMMDD>` e `3.12.4-nopy-<YYYYMMDD>`. Se já existir uma tag do mesmo dia, usa `<YYYYMMDD>.2`, `.3`... e nunca sobrescreve (a verificação usa a tag datada do `release-py`, e as três recebem o mesmo sufixo). As tags de um mesmo build saem sempre juntas: build do `devel` primeiro, depois do `release-py` e do `release-nopy`, que reaproveitam o cache. Debian, Arrow, Oracle e numpy não entram na tag. Ao mudar `GDAL_VERSION` ou `PYTHON_VERSION`, o nome das tags muda junto (as imagens derivadas recebem as versões novas pelo `dispatch`; depois, atualize os mesmos `ARG` nelas, para builds locais e manuais); os comandos de build/push estão no [README.md](README.md#build).

Verificação rápida após o build:

```bash
docker run --rm docker.io/ndscprm/gdal:3.12.4-py3.12 gdalinfo --version
docker run --rm docker.io/ndscprm/gdal:3.12.4-py3.12 ogrinfo --formats | grep -Ei 'oci|parquet|arrow'
docker run --rm docker.io/ndscprm/gdal:3.12.4-py3.12 /opt/geosgb/venv/bin/python -c "from osgeo import gdal; print(gdal.__version__)"
```

## Estrutura do Dockerfile

Cinco estágios (`staging` e `staging-nopy` são intermediários). Os nomes dos estágios finais são também os nomes das imagens no texto (README, CLAUDE.md, exemplos) e no CI: `devel`, `release-py` (com Python) e `release-nopy` (sem Python):

- **`devel`** (`python:${PYTHON_VERSION}-${DEBIAN_VERSION}`): toolchain, headers e código-fonte do GDAL. Usado para compilar código dependente do GDAL. Sem `gdb` e, com o padrão `GDAL_BUILD_TYPE=Release` (o publicado), sem símbolos de debug; com `RelWithDebInfo` (build local, para depurar), com os símbolos.
- **`staging`** (`FROM devel`, descartável): remove de `${BASE_DIR}` os arquivos só de build (`src`, `include`, `lib/cmake`, `lib/pkgconfig`, `*.a`, SDK do Oracle), faz `strip --strip-debug` em `bin`, `lib` e nos módulos `osgeo` e `pyarrow` do venv (só tem efeito com `RelWithDebInfo`; mantido para que as releases nunca levem símbolos), e gera `/tmp/runtime-packages.txt` com os pacotes Debian de runtime: roda `ldd` nos binários do GDAL (transitivo, inclui o Oracle client), resolve com `realpath` e mapeia com `dpkg -S`. O build falha se algum `ldd` der `not found` ou se uma lib não pertencer a nenhum pacote.
- **`staging-nopy`** (`FROM staging`, descartável): remove `${BASE_DIR}/venv`. Fica num estágio próprio para o venv não entrar em nenhuma camada do `release-nopy` (sem depender de `COPY --exclude`).
- **`release-nopy`** (`debian:${DEBIAN_VERSION}-slim`): igual ao `release-py`, mas sem Python. Usa a mesma lista de pacotes do `staging` mais `ca-certificates`, `netbase` e `tzdata`, que no `release-py` vêm da `python:slim` e o `ldd` não detecta (sem `ca-certificates`, o HTTPS do cURL falha). Copia `${BASE_DIR}` do `staging-nopy`, e o `ENV` não tem `VIRTUAL_ENV` nem `venv/bin` no `PATH`. Mesmo entrypoint, `CMD ["bash"]`. Fica **antes** do `release-py`, que precisa continuar sendo o último estágio (alvo padrão). Ficam de fora os bindings, o numpy e os utilitários Python do GDAL (`gdal_calc.py`, `gdal2tiles.py`, `ogrmerge.py`..., que ficam em `venv/bin`).
- **`release-py`** (`python:${PYTHON_VERSION}-slim-${DEBIAN_VERSION}`): copia os `ld.so.conf.d` do staging, instala a lista de pacotes (bind mount, sem ficar na imagem), copia `${BASE_DIR}`, recria o symlink `libaio.so.1`, repete os `ENV` e define `ENTRYPOINT ["/docker-entrypoint.sh"]` + `CMD ["python3"]`. O venv funciona porque o python das imagens `python` e `python:*-slim` fica no mesmo caminho (`/usr/local/bin`).

Etapas do `devel`, em ordem:

1. **Ferramentas de build** — `apt-get upgrade` (correções do Debian publicadas depois da imagem base) e `build-essential`, `cmake`, `wget`, `unzip`, etc. O `gdb` não é instalado (26 MB, e traz a `libpython3.13` do Debian): quem for depurar instala na hora (`apt-get install gdb`) e roda com `--cap-add=SYS_PTRACE --security-opt seccomp=unconfined` (README, "Depuração com gdb").
2. **Oracle Instant Client 19.32** (basiclite + SDK) — baixado de `download.oracle.com` (a URL é derivada de `ORACLE_INSTANTCLIENT_VERSION`), validado por SHA256 por arquitetura (`ORACLE_*_SHA256_X64` / `_ARM64`), extraído em `${BASE_DIR}/oracle`. Cria o symlink `libaio.so.1` (Debian trixie só fornece `libaio.so.1t64`) e registra o diretório do client em `/etc/ld.so.conf.d/oracle.conf`.
3. **Dependências do GDAL** — pacotes `-dev` do Debian, incluindo os usados no build do Arrow (Boost headers, codecs brotli/bz2/lz4/snappy/zlib/zstd, re2, utf8proc, RapidJSON).
4. **Apache Thrift + Apache Arrow/Parquet do código-fonte** — não usam o repositório apt do Arrow, porque os pacotes dele linkam o `libthrift` do Debian (0.19 no trixie, com CVEs abertos marcados `no-dsa`). Os tarballs vêm de `dlcdn.apache.org` (com fallback para `archive.apache.org`, para onde vão as versões antigas) e são validados por `THRIFT_SHA256`/`ARROW_SHA256`.
   - **Thrift**: só a biblioteca C++, estática e PIC (`BUILD_SHARED_LIBS=OFF`), sem compilador, TLS, zlib ou libevent. Ela fica embutida no `libparquet.so`, então não aparece no `dpkg`. Os scanners a enxergam pelo SBOM embutido (`apache-arrow.cdx.json`, com CPE), e o Grype do CI a verifica a cada build.
   - Os dois são compilados com `HARDENING_CFLAGS`/`HARDENING_LDFLAGS` (o Thrift é estático, então só as `CFLAGS` se aplicam).
   - **Arrow**: `ARROW_DEPENDENCY_SOURCE=SYSTEM`, só bibliotecas compartilhadas (`ARROW_BUILD_STATIC=OFF`), módulos `COMPUTE`, `ACERO`, `DATASET`, `FILESYSTEM`, `IPC` e `PARQUET` (usados pelo GDAL), mais `CSV` e `JSON` (obrigatórios para o pyarrow: o configure dele falha sem `ARROW_CSV`, e o módulo `_json` é sempre compilado), todos os codecs, sem jemalloc/mimalloc. O leitor JSON usa o RapidJSON do Debian (`rapidjson-dev`, só headers): ele fica compilado dentro do `libarrow.so` e não é pacote do `release-py`, então entra no `apache-arrow.cdx.json` com purl `pkg:deb/debian/rapidjson-dev@<versão Debian>?upstream=<pacote fonte>&distro=debian-<VERSION_ID>`, para o Grype usar o security tracker do Debian. `xsimd` e `simdjson` são `BUNDLED` porque o Arrow exige versões mais novas que as do trixie; o Arrow os baixa do GitHub e valida pelo SHA256 do seu `cpp/thirdparty/versions.txt` (que vem no tarball verificado).
   - Tudo é instalado em `${BASE_DIR}` (`lib`, `include`, `lib/cmake`), e `${BASE_DIR}/lib` é registrado em `/etc/ld.so.conf.d/geosgb.conf`, pois os binários instalados não têm RPATH. O `staging` remove `libthrift.a`, headers e CMake junto com os do GDAL.
5. **Virtualenv Python** em `${BASE_DIR}/venv`: `pip install --require-hashes -r requirements/gdal-build.txt` (bind mount) instala versões fixas de pip, setuptools e wheel (build dos bindings) e numpy (necessário antes do GDAL para os bindings com suporte a arrays).
6. **GDAL** — baixado de `download.osgeo.org`, validado pelo SHA256 fixo em `GDAL_SHA256`, compilado com CMake (`CMAKE_BUILD_TYPE=${GDAL_BUILD_TYPE}`: `Release` por padrão, `-O3 -DNDEBUG`; `RelWithDebInfo` com `-O3 -g -DNDEBUG`, a mesma otimização mais os símbolos; outro valor aborta o build), mais `HARDENING_CFLAGS`/`HARDENING_LDFLAGS`. Os módulos Python (`_gdal*.so`) são compilados pelo setuptools (`setup.py build_ext`), que lê `CFLAGS`/`CXXFLAGS`/`LDFLAGS` do ambiente e, quando elas existem, **descarta** as flags do Python (`-O3 ...`). Por isso o `cmake --build` recebe `CFLAGS`/`CXXFLAGS` = flags do `sysconfig` (sem os `-g*` quando `Release`) + `HARDENING_CFLAGS`. Sem isso os wrappers saem sem otimização, o que o smoke test acusa como falta de `_FORTIFY_SOURCE`; com `RelWithDebInfo`, os símbolos ficam no `devel` e são removidos no `staging`; prefixo `${BASE_DIR}`, bindings Python compilados com o python do venv e instalados nele via `GDAL_PYTHON_INSTALL_PREFIX`; `CMAKE_PREFIX_PATH=${BASE_DIR}` para encontrar o Arrow da etapa 4; build paralelo com `--parallel "$(nproc)"`).
7. **pyarrow** — depois do GDAL, para que mudanças nele não recompilem o GDAL. Baixa de novo o tarball do Arrow (mesmo `ARROW_SHA256`) e compila `python/` com `PYARROW_BUNDLE_ARROW_CPP=OFF` (padrão), linkando o Arrow C++ de `${BASE_DIR}/lib` (encontrado via `CMAKE_PREFIX_PATH`). A versão do pyarrow é sempre a do `ARROW_VERSION` (o `fallback_version` do setuptools-scm, já que o tarball não tem git). As dependências de build (cython, scikit-build-core, setuptools-scm, libcst, numpy) vêm de `requirements/pyarrow-build.txt` (hashes; numpy restrito ao do `gdal-build.in` por `-c gdal-build.in`) e ficam num venv temporário em `/tmp`, que gera o wheel com `pip wheel --no-build-isolation` (com isolamento, o pip instalaria as dependências de build sem conferir hash); o wheel é instalado no venv com `--no-index --no-deps` (o pyarrow não tem dependências de runtime). Hardening por `CFLAGS`/`CXXFLAGS`/`LDFLAGS` no ambiente, que o CMake do scikit-build-core lê; build `Release` (`-O3`). Os módulos ficam em `site-packages/pyarrow` (com `libarrow_python.so`), que o `staging` inclui no `strip` e no `ldd`.
8. `ENV GDAL_DATA=${BASE_DIR}/share/gdal`, `VIRTUAL_ENV=${BASE_DIR}/venv` e `PATH` com `${BASE_DIR}/venv/bin` antes de `${BASE_DIR}/bin` (o `python`/`pip` do shell resolvem para o venv, sem precisar de `activate`).

## Convenções

- `SHELL` usa `bash -o pipefail` no `devel` (volta para `/bin/sh -c` no final) e no `staging`; o `release-py` usa o shell padrão.
- Cada `RUN` com apt faz `update`, `install --no-install-recommends --no-install-suggests`, `autoremove` e apaga `/var/lib/apt/lists/*`. O primeiro `RUN` do `devel` e o `RUN` de pacotes do `release-py` fazem também `DEBIAN_FRONTEND=noninteractive apt-get -y upgrade` logo após o `update`, para aplicar nos pacotes da imagem base as correções do Debian publicadas depois dela.
- Todo download externo é verificado contra um valor fixado no repositório (SHA256 do Oracle, do Thrift, do Arrow e do GDAL no Dockerfile; hashes dos pacotes do venv em `requirements/gdal-build.txt`), nunca contra um checksum baixado do mesmo servidor. Ao atualizar uma versão, atualize também o checksum/fingerprint correspondente.
- A arquitetura do Oracle é derivada de `dpkg --print-architecture` (`amd64` → `x64`); arquiteturas diferentes de x64/arm64 abortam o build.

## Pontos de atenção (estado atual)

- **Drivers opcionais**: `GDAL_BUILD_OPTIONAL_DRIVERS=OFF` e `OGR_BUILD_OPTIONAL_DRIVERS=OFF` desativam todos os drivers opcionais; OCI, Arrow, Parquet, OpenFileGDB, PostGIS (`PG` + `PGDump`, e `POSTGISRASTER`) e GeoPackage (`GPKG` + `SQLite`, com `PNG`/`JPEG` para tiles raster) e serviços OGC (`WMS`, `WCS`, `OGCAPI`, `WFS`, `OAPIF`, mais `RAW` exigido no configure pelo WMS, e `GML` e `MVT` usados em runtime por WFS e OGC API Tiles) KML/KMZ (`KML` e `LIBKML`) e `Elasticsearch` (`ELASTIC`, via cURL) são habilitados explicitamente (`OGR_ENABLE_DRIVER_*`/`GDAL_ENABLE_DRIVER_*=ON`), com `GDAL_USE_ORACLE/ARROW/PARQUET/POSTGRESQL/SQLITE3/CURL/EXPAT/LIBKML=ON` para o configure falhar se a dependência não for encontrada. Qualquer outro driver opcional precisa ser adicionado da mesma forma.
- **Símbolos de debug só com `GDAL_BUILD_TYPE=RelWithDebInfo` (decisão)**: o `devel` publicado (`Release`) não tem símbolos nem `gdb`, cerca de 400 MB a menos (a `libgdal.so` tinha 337 MB com símbolos e 22 MB sem), o que pesa porque ele é baixado a cada build das imagens derivadas. O build type só muda os símbolos: o código-fonte do GDAL fica em `${BASE_DIR}/src/gdal-${GDAL_VERSION}` nos dois casos (consulta e depuração; os símbolos do `RelWithDebInfo` apontam para ele), e só o `build/` é removido após o install. O código de máquina é o mesmo nos dois (`-O3`), então um core dump do `release-py` pode ser aberto num `devel` `RelWithDebInfo` do mesmo commit. O `cd` para o build fica num subshell `( ... )`, então comandos após o `)` rodam em `/tmp`.
- **SBOM**: os pacotes Debian e Python entram no SBOM do BuildKit automaticamente, mas o que é compilado ou baixado fora do apt não. Por isso cada etapa que instala algo assim grava um CycloneDX em `${BASE_DIR}/share/sbom/*.cdx.json` com [sbom/cyclonedx.py](sbom/cyclonedx.py) (`RUN --mount=type=bind,source=sbom/cyclonedx.py,...`): `oracle-instantclient`, `apache-arrow` (arrow, thrift, xsimd, simdjson, rapidjson; as versões de xsimd/simdjson vêm do `versions.txt` do Arrow e a do rapidjson do `dpkg-query`) e `gdal`. O Syft do BuildKit incorpora esses componentes na attestation. Componente com CVE conhecido precisa de `cpe` (vendor/produto da NVD); o Oracle fica sem CPE de propósito, porque os CPEs da Oracle na NVD são do servidor de banco e dariam falsos positivos. **Novo componente fora do apt = nova entrada no SBOM** (o smoke test confere os nomes esperados).
- Os pacotes de runtime do `release-py` e do `release-nopy` não são listados à mão: vêm do `ldd` no `staging`. Ao adicionar um driver/dependência, não é preciso mexer no `release-py` nem no `release-nopy`. Pacotes que o GDAL só carrega em runtime sem linkar (ex.: dados) precisam ser adicionados explicitamente (no `release-nopy`, também os que o `release-py` recebe de graça da `python:slim`).
- **Entrypoint (`devel`, `release-py` e `release-nopy`)**: definido no `devel` (que o `staging` herda); o `release-py` e o `release-nopy` copiam `/docker-entrypoint.sh` e `/docker-entrypoint.d` do `staging` com `COPY --from`, que preserva os modos, para as três imagens terem sempre o mesmo entrypoint. [docker-entrypoint.sh](docker-entrypoint.sh) (POSIX `sh`) percorre `/docker-entrypoint.d` em ordem léxica — mesmo modelo da imagem oficial do Postgres: `*.sh` com `+x` são executados, `*.sh` sem `+x` são carregados com `.` (variáveis exportadas chegam ao comando; `exit` neles, mesmo `exit 0`, interrompe o start), o resto é ignorado. Termina com `exec "$@"`. A permissão define o modo, então imagens derivadas devem usar `COPY --chmod`. Script com erro aborta o start (`set -e`). `ENTRYPOINT_QUIET_LOGS` silencia os logs. O `CMD ["python3"]` é explícito porque definir `ENTRYPOINT` zera o `CMD` herdado da imagem `python`; imagens derivadas que definirem só `CMD` continuam passando pelo entrypoint.
- **nss_wrapper (`devel`, `release-py` e `release-nopy`)**: o pacote `libnss-wrapper` é instalado explicitamente nos três estágios (no `release-py` e no `release-nopy`, à parte da lista do `ldd`, porque é carregado via `LD_PRELOAD` e não linkado) e [10-enable-nss-wrapper.sh](docker-entrypoint.d/10-enable-nss-wrapper.sh) (sem `+x`, portanto carregado com `.`) cria, quando o UID do container não existe no `/etc/passwd` (ex.: OpenShift, `--user`), um usuário virtual `${USER_NAME:-sgb}` e exporta `NSS_WRAPPER_PASSWD`, `NSS_WRAPPER_GROUP` e `LD_PRELOAD=libnss_wrapper.so`. Os arquivos `passwd`/`group` virtuais ficam num diretório criado com `mktemp -d` (`${TMPDIR:-/tmp}/nss_wrapper.XXXXXX`, modo 0700), nunca num caminho fixo do `/tmp`, que poderia ter sido plantado antes (ex.: symlink num `/tmp` compartilhado entre containers). `USER_NAME` (letra ou `_` no início, depois `[A-Za-z0-9._-]`, até 32 caracteres) e `HOME` (sem `:` nem quebra de linha) são validados antes de entrar na linha do passwd; valor inválido aborta o start com mensagem no stderr. Com o usuário virtual, também exporta `HOME=/tmp` se o `HOME` estiver vazio ou for `/` (o Docker usa `/` para UID sem passwd). Um `HOME` não gravável é mantido de propósito (sem teste `-w`): com `--read-only` ele nunca é gravável, e imagens derivadas que guardam a configuração no `HOME` (ex.: mapproxy-oci) deixariam de encontrá-la em `/tmp`. A mensagem vai para o stderr e respeita `ENTRYPOINT_QUIET_LOGS` — scripts em `docker-entrypoint.d` nunca devem escrever no stdout, que é a saída do comando (ex.: `/vsistdout/`). Os scripts de `docker-entrypoint.d/` são copiados um a um com `COPY --chmod` explícito (o modo define executar vs. carregar, e não pode depender da permissão no disco); o diretório é criado antes com `RUN mkdir -p`, porque `COPY --chmod=644` também aplicaria `644` ao diretório e ele deixaria de ser acessível para usuários não root. Novo script no repositório = nova linha `COPY` no bloco do entrypoint do `devel` (o `release-py` e o `release-nopy` recebem o diretório inteiro). Os scripts precisam funcionar sem Python (o `release-nopy` não tem).
- **pip do sistema removido (`devel` e `release-py`)**: a imagem `python` traz um pip próprio em `/usr/local` (desatualizado, com CVEs) que ninguém usa, porque `pip` resolve para o venv. Ele é desinstalado com `/usr/local/bin/python3 -m pip uninstall`. O wheel do `ensurepip` fica, então `python3 -m venv` continua criando venvs com pip nas imagens derivadas (o smoke test confere as duas coisas).
- **Abertura de arquivos não confiáveis**: o README tem uma seção ("Abrindo arquivos enviados por usuários") com riscos e mitigações testados nesta imagem: SSRF via `.vrt` com `/vsicurl/` e via XML do driver WMS, `allowed_drivers`, `GDAL_SKIP`. Ao habilitar drivers de rede ou que abrem outros datasets, revisar essa seção.
- **Dependências do venv fixadas com hash** ([requirements/gdal-build.in](requirements/gdal-build.in) → [gdal-build.txt](requirements/gdal-build.txt)): para mudar uma versão (inclusive o numpy, que antes era o build arg `NUMPY_VERSION`), editar o `gdal-build.in` e regenerar o `gdal-build.txt` com o comando do cabeçalho do `gdal-build.in`. O pip-compile grava os hashes de todos os arquivos da versão no PyPI, cobrindo amd64/arm64 e outras versões do Python. O Dependabot (ecossistema `pip`, diretório `/requirements`) abre PR semanal com atualizações, **exceto do numpy** (`ignore` no [dependabot.yml](.github/dependabot.yml)): ele é fixado nos dois `.in`, e um PR que mudasse só um deles quebraria o build. O numpy é atualizado à mão, nos dois arquivos juntos (abaixo); CVEs dele continuam aparecendo no scan do CI. Manter numpy 2: bindings compilados com numpy 2 rodam com 1.x e 2.x; compilados com 1.x quebram (`ImportError`) quando a imagem derivada instala numpy 2. O smoke test confere se as versões instaladas são as do `gdal-build.txt`. As dependências de build do pyarrow seguem o mesmo esquema em `pyarrow-build.in` → `pyarrow-build.txt` (comando no cabeçalho do `.in`); o numpy precisa ser o mesmo nos dois (fixado nos dois `.in`; o `-c gdal-build.in` faz o pip-compile falhar se divergirem, e o Dockerfile aborta se o numpy do venv temporário for diferente do venv da imagem), então ao mudar o numpy no `gdal-build.in`, mudar também no `pyarrow-build.in` e regenerar os dois `.txt`. O pyarrow não está no `gdal-build.in`: a versão vem do `ARROW_VERSION`, e um `pip install pyarrow` numa imagem derivada o trocaria pela wheel do PyPI, com um Arrow C++ próprio (o README explica).
- **Imagens base por tag, sem digest (decisão)**: `FROM python:${PYTHON_VERSION}-${DEBIAN_VERSION}` (e `-slim-`, e `debian:${DEBIAN_VERSION}-slim` no `release-nopy`) sem `@sha256`, para o rebuild semanal pegar a base atualizada automaticamente. Fixar o digest exigiria o Dependabot, que não entende `FROM` com `ARG`, ou atualização manual, e a base só atualizaria quando alguém aprovasse a mudança. A reprodutibilidade vem do provenance (`mode=max` registra o digest exato de cada base em `materials`) e das tags datadas.
- `ENV` é repetido no `release-py` e no `release-nopy` (não é herdado entre estágios com `FROM` diferentes); manter os três em sincronia (o `release-nopy` sem `VIRTUAL_ENV` e sem `venv/bin` no `PATH`).
